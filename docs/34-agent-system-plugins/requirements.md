# 第 34 轮 · 适配日常的动态教练、插件与记录可靠性

## 依据与目标

2026-10-17 用户要求恢复 Moveliq 内置浏览器，并解决本次检查发现的问题；随后要求系统能力统一做成 App 内的 Agent 插件，尤其是管理日历。用户设备为 iOS 26 或更新版本；确认浏览器优先使用 App 内网页，由用户确认提取内容。Siri 仅作为调用 Moveliq 动作的入口，不作为 Agent 操作其他 App 的通道。

用户进一步明确产品目标：真正的健身教练应结合日常生活规划，并随变化动态调整。插件是获取上下文、落实安排和辅助训练的能力；验收以“了解生活 → 制订可执行计划 → 执行 → 根据反馈调整 → 持续复盘”的闭环为核心，不能以插件已连接或一次生成课表代替。

2026-10-17 用户回复“没问题，就开发吧”，确认本轮 13 屏设计及对应实施范围；随后回答自主程度为“在我预先设定的范围内自动调整，其余再确认”。该最新选择取代此前所有调整都确认的临时假设。已确认的是授权模式，具体额度仍由用户在 App 设定，不从此回复推断任意分钟数、幅度或系统写入范围。新增授权配置/执行回执交互另出设计；独立的非 UI 规则与校验可先开发。源码实施与原生/真机验收分别记录在 checklist。

## R0 · 适配日常的动态教练（核心体验；涉及 UI）

### 建立可更新的个人约束

- 结合用户明确的目标、训练经验、偏好、器械/场地、每周可投入次数、单次可用时长和作息安排规划。区分必须遵守的限制与可协商偏好；未知信息先询问或标为未提供，不从日历空白推断“有空且能训练”。
- 日历提供用户选定范围内的忙闲摘要；安排时考虑用户设定的通勤、准备/洗漱、用餐和休息缓冲。通勤仅使用用户给定地点或当次授权地图查询结果，不持续追踪位置。
- 身体与完成情况来自当前可用的本地聚合摘要：最近训练、实际组次/重量/时长、完成/跳过、睡眠/活动等已同步健康数据，以及用户明确反馈的精力、酸痛、压力和可用时间。显示时间范围与更新时间，缺失/过期不当作正常、零值或今天数据。
- 长期目标和生活偏好需用户可查看、修改或删除；“今天累/本周出差”等临时状态有有效期，不永久写成用户特征。变化的日程不固化进长期记忆。

### 制订能执行的计划

- 先核对目标与必要约束，再提出未来一周可执行安排和较长期的训练方向；每次安排明确时间窗口、场地/器械、预计训练时长与主要目标。只有可用时长或只有忙闲摘要时，如实说明约束不足。
- 保留原有课程草稿确认流程。展示关键安排原因，例如“周二有晚间日程，因此放到周三”；理由必须对应当次实际查询或用户反馈，不编造同步状态、恢复评分或健康结论。
- 在时间不足或行程变化时可提出缩短、移动、替换、减少/增加频次或休息等方案，并说明对近期目标的影响。不能机械顺延、挤满空闲时段，或把未完成内容全部堆到下一天。
- 已完成训练和原始日志保持不变；调整针对明确的未来计划日/动作。实际执行偏离计划可以被记录，用于下一次规划，不“修正”历史日志来匹配计划。

### 变化触发重新评估

- 支持用户提出变化（“今天只有 20 分钟”“临时加班”“这周出差”）、训练完成/跳过、应用可观察到的日历变化和健康摘要更新后重新评估；进入 App 的每日检查也可发现待处理冲突。一次变化不必重写整份计划。
- 同一事件聚合去重；若已有待确认调整，更新/作废旧提案，不反复生成相互冲突的卡片或提醒。重新规划前查询最新计划版本、相关日程和数据新鲜度。
- 展示“为什么调整、原来怎样、现在怎样、影响哪些日期/动作/提醒”。在用户已保存且仍有效的授权范围内可自动执行并给出回执；超出范围、必要信息缺失或需要澄清时先确认。自动调整后的恢复原安排也要重新检查最新冲突，不能以无条件撤销覆盖新日程。
- 一项建议可涉及课程表、关联日历与闹钟。用关联 ID 和操作批次协调，分别记录真实结果；跨 SwiftData / EventKit / AlarmKit 不假装有单一原子事务。部分成功时明确展示已完成/未完成项，重试只补未完成项，不重复创建事件或闹钟。
- 不将外部普通日程当成可随意移动的训练记录；只对用户明确选择的日程/插件执行允许的动作。课程表调整不默认移动会议、取消他人活动或改系统既有闹钟。
- “主动”以实际可观察的触发事件为基础。前台/再次打开时可刷新评估，已安排提醒由系统处理；后台刷新仅按 iOS 允许的时机执行，不承诺持续驻留、全天候实时发现和静默运行云端 Agent。未能及时刷新时展示数据时间。

### 训练后反馈与持续复盘

- 训练后轻量确认实际完成、难度与主观状态，可跳过或稍后补充；反馈只填写本次必要内容，不强迫长问卷。系统读取的运动不自动当作已完成某个课程日，匹配需可靠依据/用户确认，避免双计。
- 每周结合实际完成与生活约束，回顾哪些安排可执行、哪些需要调整，提出下周具体变化；不只汇总训练次数，也不将漏记判定为不努力。
- 数据不足时给出有限结论并提供补充入口。疼痛/身体不适不能仅凭健康指标或模型推断诊断、以“恢复分高”覆盖用户反馈；健康数据使用与训练建议保持可解释且可拒绝。

### 核心场景验收

1. 初次规划：用户可训练时段与所选日历均被纳入；硬限制不被违反，缺失信息不被编造。
2. 临时加班：受影响的训练被明确定位，建议可执行的新时段/短版本；不修改无关生活事件，不改变已完成记录。
3. 当日状态变化：结合当前反馈与可用摘要说明调整依据；睡眠/活动数据缺失或过期时如实提示，不生成伪精确的恢复分。
4. 漏练/额外运动：重新评估后续安排，不堆叠补课、不重复统计；用户可保留原计划。
5. 接受调整：计划、关联日历/提醒的结果可核对；重复确认、版本变化、部分失败及重试不会造成重复或错误覆盖。
6. 长期复盘：上周的执行与约束能影响下周建议；临时状态到期后不继续误用，用户可修改教练记住的偏好。

插件按支撑闭环的顺序实施：个人约束/现有训练与健康摘要 + 日历 → 规划与动态调整 → 执行反馈/复盘 → 浏览器/地图/闹钟/音乐及 Siri 辅助入口。各插件继续保持独立启用，关闭辅助插件不阻断基础教练与记录。

### R0-A · 用户预设范围内的自动调整（追加）

- 在“我的训练与日常”提供授权规则入口：选择适用的课程表、可自动执行的操作类型、允许移动的分钟/天数、训练时长底线及最大缩短比例、减重幅度、每日调整次数、开始前停止自动调整的时间和未来计划范围。未保存完整规则前不启用，不替用户填入实际授权额度。
- 首批可分别授权：移动时间、缩短时长、降低已有动作重量、跳过本次训练。换动作、加重量/加时长、增加次数、创建或删除课程表、改变目标仍需确认。用户可只选择其中一项，也可随时停用、修改或清除规则。
- 本地课表授权与关联日历/关联闹钟同步分别授权；启用日历/闹钟插件本身不代表允许自动写入。仅涉及 Moveliq 的训练关联对象，外部会议、其他日程以及独立的日历/闹钟操作继续走确认卡。
- 自动执行前由本机可信代码核对账号、规则、方案/日程版本、数据新鲜度、当前完整硬约束、进行中的训练及适用计划。疼痛/不适或存在未澄清的重要状态时先询问；模型不能自行授予权限、修改限额或把数据缺失解释为可执行。
- 整批变更必须都在范围内；任意一项越界则整批转待确认，不先自动执行其中一部分。每天次数按实际变更条数累计；同一训练日的连续移动、缩短、减重相对本轮授权下的原始锚点计算，不能通过多次小调整绕过总幅度限制。
- 自动执行保留触发原因、授权版本、原安排/新安排、时间、操作 ID 及分步同步结果。重复触发不重复执行；关闭授权、规则过期、换账号或状态变化后，尚未执行的自动任务失效；部分完成不重复写入，重试前检查剩余步骤仍被授权。
- 自动触发以 App 实际能观察到的前台/再次进入事件为基础；已安排的提醒由系统运行，不承诺 App 被挂起后持续运行云端 Agent。
- 新交互见 [自动调整追加设计](design.autonomy.html)。该追加稿独立于此前已确认的 13 屏；当前先实现非 UI 的授权持久化与本机判定器，设置界面、自动执行器及触发接线在追加稿确认后开发。

2026-10-17 用户反馈追加界面“有些丑”。第二版沿用现行 Journal 浅深色与暖橙强调色，改为简洁的授权概览、按需展开的边界编辑、突出时间变化的自动调整回执和明确的单次确认；避免首页堆叠数字输入、复选框与大段说明。保留全部授权范围，不用简化视觉掩盖实际权限。先修改设计稿并完成渲染检查，再确认新增 UI；不修改此前确认的原生界面。

2026-10-18 用户在第二版预览后明确要求“继续开发吧，开发完成，打IPA”。按该版设计完成接入，执行必要的提交/推送、CI 验证和 IPA 打包，并交付实际下载链接；真机授权、响铃、音乐、定位及 Siri 结果仍如实区分。

## R1 · 插件基础与设置（涉及 UI，设计确认后接入）

- 新增统一插件管理入口：日历、内置浏览器、地图、闹钟、Apple 音乐；Siri 与快捷指令列为系统入口集成。每项分别显示启用状态、系统授权和需要完成的设置，不能把 App 内开关当成系统授权已获准。
- 插件注册、参数校验、工具执行及系统访问放在 App 层的适配边界；Agent 仍只处理 DTO、摘要及工具协议，不直接操作 EventKit、MapKit、AlarmKit、WebKit 或数据库。
- 只向模型暴露当前账号已启用且可用的工具；执行时再次检查账号代次、插件开关、授权、参数、目标与确认状态。关闭插件、退出账号或取消时，旧请求不可继续执行或覆盖新会话。
- 插件偏好按账号隔离；系统权限属于设备，不因换账号自动视为用户已经启用插件。已交给系统的日程/闹钟保留，关闭插件和退出登录不暗中删除它们。
- 保留 iOS 17 最低运行版本，系统能力按 availability 降级；闹钟要求 iOS 26 和相应 SDK。此次不恢复本地模型、下载或推理。

## R2 · 日历管理（本轮重点；涉及授权与确认 UI）

- 通过 EventKit 查询用户选定的日历、日期范围内的日程，计算空闲时段；支持创建、修改、删除日程，包含标题、起止时间、全天、地点和提醒。默认按当前时区解释自然语言；日期、时区或目标存在歧义时先确认。
- 查询/管理需日历完整访问；只授予添加权限时可添加但不能宣称已读取日程。展示未请求、仅添加、完整访问、拒绝、受限制、日历失效/只读等状态，并可跳转系统设置。
- 用户选择允许读取的日历及默认写入日历；写入前验证目标日历仍存在且允许修改。只读订阅和他人日历遵守系统实际权限。
- 查询有明确日期边界及数量上限；只返回完成当前请求所需的日程摘要和临时代号，不发送备注、参与者、会议链接、附件或整库。空闲计算、过滤与原始事件解析在设备上完成。
- 新增、修改和删除均生成待确认操作卡；模型不直接写入。确认卡展示准确日期、时间、时区、目标日历、变化前后与提醒。多候选须先选择明确对象；不能仅凭标题匹配后删除。
- 修改前重新读取对象并校验版本；事件被外部修改或删除后重新查询/确认，禁止用过期快照重建已删除事件。确认动作只执行一次，双击/重复工具输出不重复创建。
- 重复事件必须明确选择“仅此次”或“此次及以后”；未选范围不得修改/删除系列。新增支持基本按天/周重复及结束条件，不能静默替换复杂重复规则。
- 监听事件库变化并使旧摘要/确认失效；处理同步失败、权限撤销、跨午夜、夏令时、只读日历、提醒与时间冲突。系统日历为日程权威来源，不复制一套全量日历数据库到 SwiftData。
- 本轮“后台功能”指直接使用系统 API。已保存日程及其提醒由系统处理；不承诺 App 被挂起后 Agent 持续运行或后台主动重排日程。

## R3 · 内置浏览器（涉及交互，确认后实施）

- 与 `useLocalModel` 解耦。云端 Milo 和课程教练优先通过内置浏览器执行公共主题搜索/网页阅读，不再要求本地模型开启。
- 沿用可见网页和手动提取：搜索完成后“使用搜索结果”，正文页“让 Milo 阅读这页”；用户返回对话、关闭或停止生成时及时结束等待，不能卡住工具请求。
- 链接在允许的 HTTPS 来源内用内置预览；沿用现有来源范围和隔离会话，不把范围外网页默默视为已读。为不支持的链接明确提供系统浏览器入口。
- 搜索只发送公共主题关键词，不附加对话或健康数据；提取结果标注为不可信引用且有大小上限。载入、空结果、网络失败、页面变化、超时和手动验证状态可重试/退出，不伪造结果。
- 既有云端搜索实现保留兼容性，本轮默认浏览器路径不依赖服务端搜索接口是否开启，也不静默调用付费搜索代替失败的内置浏览器。

## R4 · 地图插件（涉及 UI）

- 使用 MapKit 搜索地点、展示候选、查看路线及打开 Apple 地图；由用户选择目的地/出行方式后打开系统地图。
- 使用用户输入的地点可不申请定位；需要“附近”或当前位置时，按需申请使用期间定位。拒绝时允许手填起点，不申请持续后台定位。
- 将地点和路线摘要返回当前对话；不上传位置历史，不把打开地图误报为已经开始导航/已经到达。

## R5 · 闹钟插件（涉及 UI，iOS 26+）

- 通过 AlarmKit 申请独立闹钟权限，管理 Moveliq 自己创建的闹钟/倒计时：创建、查看、调整、取消，支持一次性及每周重复。
- 创建/修改/取消先展示具体时间、重复日期、标签及作用范围供用户确认；成功状态仅以系统 API 结果为依据，失败可重试且不重复安排。
- 不承诺读取或管理系统“时钟”App 的全部既有闹钟。旧系统展示不可用，不用普通通知冒充 AlarmKit 闹钟。

## R6 · Siri / 快捷指令入口（涉及系统交互）

- 使用 App Intents / App Shortcuts 让 Siri 调用 Moveliq 的动作：打开 Milo、查看今日训练、准备一条记录草稿。记录和系统写入继续遵守原有确认边界。
- 按当前账号和插件可用性处理入口；未登录先打开 App 完成登录，不在锁屏语音中泄露健康/日历详情。具体短语及跳转见设计稿，待用户确认。
- 不实现“把文字交给 Siri 让其代操作其他 App”，不申请不存在的统一系统控制权限。

## R7 · Apple 音乐插件（用户追加；涉及 UI）

- 接入 Apple 自带“音乐”，使用 MusicKit 的 SystemMusicPlayer 控制其播放状态：播放、暂停、继续、上一首/下一首、查看当前曲目；支持搜索歌曲、专辑和歌单，再选择结果播放。替换当前播放队列前说明目标并确认，不把请求接受误报为已经播放。
- 使用 MusicAuthorization 按需请求媒体/Apple Music 访问，配置 NSAppleMusicUsageDescription。分别展示未授权、拒绝/受限制、可用内容、播放失败及离线状态。
- 检查 MusicSubscription 的实际能力；Apple Music 曲库完整播放取决于订阅和地区可用性。未订阅不阻止使用设备实际可播放的已购买/同步音乐；不假定所有媒体库内容离线可播。
- 搜索/播放先使用设备 MusicKit 能力；只把完成当前请求所需的候选曲名、歌手、标识和播放状态摘要给 Agent，不上传全量音乐库或音频。不以本插件控制其他音乐 App。
- 音乐播放与语音转写、实时通话、训练提示的音频路由/中断须在真机验证。关掉插件停止 Agent 后续控制，不擅自清空系统播放队列。
- 核对开发者 App ID 的 MusicKit App Service、bundle ID 和最终侧载签名。自动 developer token 依赖服务配置；不能将“App 编译成功/权限已授予”视为曲库 API 已可用，不将私钥放入 App 或仓库。
- 歌单编辑暂列后续能力，首轮聚焦搜索、选择和系统播放控制；新增歌单写入需求另行细化，不能以播放权限暗中修改用户音乐库。

## R8 · 本次检查发现的问题（独立非 UI 修复可先实施）

- 兜底 RawNote 保存错误必须传递到调用方；只在持久化成功后显示“已保存”。失败时保留当前输入/照片和重试所需内容，显示未保存状态。
- 同轮多条草稿和对应照片作为一次提交：全部持久化成功后才标记本轮已保存；失败保留全部可编辑草稿并允许重试，不出现部分成功后整轮被锁定或重试重复写入。照片直接关联本次创建的餐食，不查询“最近一餐”碰运气。
- 清空/关闭使解析请求失效，并取消当前解析任务；旧结果、旧错误及旧 defer 不得改写下一次解析的状态。显式清空的输入不在旧回调中重新保存。
- Python 文本读写明确 UTF-8，覆盖中文 Windows 默认编码场景。
- 更新 README 当前版本/轮次与停用本地模型状态；docs 索引引用 AGENTS 公共规则，删除与其冲突的重复约定，不篡改历史轮次验证结果。
