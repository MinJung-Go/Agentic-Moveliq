# 第 35 轮 · 一键连接所选服务

## 用户目标与范围

2026-10-18 用户认为插件设置复杂，希望一键授权选定的服务；在了解“选择服务 → 一键连接 → 系统弹窗逐项允许”的方案后回复“可以，开发吧”。本轮简化第 34 轮的插件连接流程，保留各项实际授权、账号隔离和日历数据范围，不扩大 Agent 操作权限。实时通话的插件接入暂不需要。

## R0 · 首次安装主动引导（用户追加）

2026-10-18 用户补充：“应该是用户初次安装，就弹连接授权”。首次成功登录并打开账号数据后，主动展示服务连接引导；放在进入首页之前，不要求用户先找到设置。不在登录前保存账号偏好或抢弹系统授权。原欢迎说明压缩到引导页头，原单独的健康授权合并到服务选择，避免重复引导。

- 提供“连接所选服务”和“稍后再说”；无论部分授权还是跳过都可使用基本记录/对话。记录完成/跳过状态，不因拒绝权限、重新启动、普通升级反复强制弹出。
- 首次进入某账号可建立该账号的选择，但不把另一账号的服务选择复制过来；已有账号升级后从设置补连，不以升级为由强制弹首次引导。连接中途退出且未完成/跳过时，下次可继续展示引导，重新核对已有系统授权。
- 复用同一连接界面作为“设置 → 插件”的补连入口。系统已授权不等于当前账号已启用，各自保持独立。

## R1 · 一个连接入口

- 连接页展示健康、日历、闹钟、Apple 音乐、地图、内置浏览器六项服务、各自用途、选择状态及实际连接状态；健康复用原授权流程，其他五项复用插件。选择按当前账号保存；初始选择沿用现有配置，健康未选择时不申请，不替用户全选。
- 卡片选择先作为当前页面草稿，点击连接后保存到当前账号；直接跳过不提交尚未连接的勾选。新账号跳过时不继承设备上其他账号的健康接入，已有账号升级保留旧健康行为；关闭健康连接停止后续导入，保留已有记录。
- 一个“连接所选服务”按钮依次处理所选服务。只请求未决定的权限，已授权直接检查结果；浏览器无系统权限弹窗。Apple 音乐的“已授权”不等同于已订阅或保证曲库可播放。
- 内置浏览器被选中并点击连接时，启用现有可见网页搜索入口；仍由用户主动提取网页内容。仅打开页面不修改联网搜索偏好。
- 地图连接请求使用期间定位，明确用于附近地点；不在连接时采集位置，不申请后台定位。拒绝定位后仍可使用手填地点和地图路线。
- 健康仅请求已有只读类型。HealthKit 不提供各类读取权限的完整可见结果，流程完成只显示“已完成授权选择”，不报告“全部已授权”、不将无数据当作已拒绝；签名/系统不支持与请求失败按真实状态提示。
- 一个权限结束并恢复 App 活跃状态后再申请下一项，不并发堆叠系统弹窗。用户可停止后续连接，已授予的系统权限保留；页面退出、账号改变或 App 进入后台时停止队列，原授权弹窗本身由系统管理。
- 连接期间阻止重复启动及修改选择；授权返回后复查账号和批次代次，旧结果不能写入新账号或覆盖新一轮结果。

## R2 · 清晰且可恢复的结果

- 区分未请求、处理中、已授权/可用、待选择日历、被拒绝/需前往设置、受限制、当前系统不支持、请求失败、未处理。拒绝一项可继续其余所选项，不宣称全部连接成功。
- 已拒绝的权限不反复申请，提供统一“前往系统设置”入口；受限制/旧系统单独解释，不暗示去设置一定能解决。返回前台重新读取系统状态。
- 保留已有的日历选择与默认写入日历；第一次完整授权后不自动读取全部日历或代选范围。日历范围为空/失效时提示“选择日历”，展开必要设置；选择完成后更新状态。
- 浏览器可用、地图手填可用、音乐授权等状态按实际能力描述，不把权限开关当成实际搜索、播放或响铃验证。

## R3 · 详细设置折叠

- 默认折叠“详细设置”，保留允许查询的日历、默认写入日历、关联训练日历/闹钟同步、提醒提前量、选择训练音乐及 Siri 入口。
- 必要配置未完成时定向展开对应内容。已有配置保持不变；不自动开启训练同步、扩大日历范围、修改自动调整额度或替用户创建任何日程/闹钟。
- 沿用 Journal 浅深色、暖橙主按钮及系统样式；覆盖 320pt、小屏滚动、大字体、VoiceOver、连接中、部分完成、空选择和旧系统。

### 第二版视觉调整（2026-10-18）

用户评价初稿“有些 ugly”，具体设计未获确认。重做为首次启动的底部连接卡：Milo 欢迎区、两列服务选择卡片及一个连接主按钮；缩短标题和重复说明，详细设置继续折叠。连接中聚焦当前服务和简短进度，结果页突出已完成数量与确需处理的项目，不再重复整页选择列表。保留全部真实授权状态、范围选择、暂停、跳过及设置补连能力。先渲染第二版并供用户查看，再接入原生页面。

## 实施与验收

先写本需求和 checklist，完成可查看的具体设计稿，确认后接入 SwiftUI；独立的授权队列及策略可先实施。本次“开发吧”确认产品方案，不记录为尚未生成的具体设计稿已获确认。

2026-10-18 用户对第二版明确回复“按第二版接入”，已确认该版具体界面，推进首次引导与设置补连的原生实施。

1. 仅选日历、闹钟时，依次请求这两项，音乐/定位不弹窗；已授予的权限不重复询问。
2. 日历允许、音乐拒绝、闹钟允许时保留各项真实结果，并支持去设置；无批次成功假象。
3. 空选择无请求；浏览器不请求权限；地图定位拒绝不阻断手填地点。
4. 连接中双击、停止、后台、退出、账号切换及晚到回调不导致重复申请或跨账号写入。
5. 首次日历授权后须选择范围；已有范围保留，失效项不默认为全部。训练同步和自动调整规则不被本轮连接流程扩大。
6. 模拟队列的单测、设计稿的交互/布局检查、原生编译与真机授权分别记录。Windows 本机不声称运行 Xcode；真机授权状态不能由 HTML 示意证明。
7. 新安装登录后自动展示；跳过、部分完成、重启与普通升级不反复打断。账号切换遵守本账号的引导和选择，原健康入口仍可补授权。

## 平台依据

- [Apple：请求受保护资源](https://developer.apple.com/documentation/uikit/requesting-access-to-protected-resources)：系统按资源请求，用户决定允许/拒绝，既有决定及设置变更须检查。
- [Apple：iOS 运行时与沙盒](https://support.apple.com/zh-cn/guide/security/sec15bfe098e/web)：仅使用系统公开服务，无法取得其他 App 的全部权限或私有数据。
- [Apple：健康数据授权](https://developer.apple.com/documentation/healthkit/authorizing-access-to-health-data)：App 无法获知各读取类型是否被拒绝，完成授权流程不等于所有类型均被允许读取。
